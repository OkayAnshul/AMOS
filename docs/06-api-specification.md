# 06 — API Specification

Conventions and contracts. The machine-readable schema is generated by FastAPI at
`/openapi.json` and `/docs`; this document covers what OpenAPI cannot express — versioning
policy, the error envelope, status-code semantics, and why each endpoint is shaped as it is.

**Current version: read it from `/health`.** It comes from `amos.__version__`, which is the
single definition the build derives from. This line used to say "V0.1" and the `/health` example
below used to show `"0.1.0"` — both long after V1.0 shipped, which is the same class of drift
that had the OpenAPI description reading "V0.7" on a v1.0 build.

## Conventions

- Versioned path prefix `/v1/`. Unversioned paths (`/health`) are operational, not product API.
- Request and response bodies are JSON. Every field is validated by Pydantic at the boundary.
- Every response carries an `x-request-id` header. A client-supplied `x-request-id` is honoured
  and echoed, so client and server logs correlate. Since V0.9 it is also the OpenTelemetry span
  attribute that ties logs to traces.

## Endpoints

There are **five**, all in `src/amos/api/app.py`.

| Method | Path | Purpose | Success |
|---|---|---|---|
| `GET` | `/health` | liveness | `200` |
| `POST` | `/v1/goals` | run a goal synchronously | `200` |
| `POST` | `/v1/goals/async` | queue a goal for a worker | `202` |
| `GET` | `/v1/runs/dead-letter` | runs the queue gave up on | `200` |
| `GET` | `/v1/runs/{run_id}` | the full trace of a past run | `200` |

### `GET /health`

Liveness. Returns `{"status": "ok", "version": "<amos.__version__>"}`. No auth, no dependencies
checked — deliberately shallow, so it stays fast and cannot fail for reasons unrelated to the
process being alive.

**There is no readiness probe.** An earlier version of this document promised one "with the
database at V0.3"; it was never built, and the promise is withdrawn here rather than left
standing. `docs/18-deployment.md` records the same gap.

### `POST /v1/goals`

Runs the goal in the request. Blocks until it completes.

**Request**
```json
{ "goal": "string, 1..8000 chars" }
```

**Headers** — `idempotency-key` (optional). A resubmission with the same key returns the
**original** run rather than executing again. This is requirement F-9, and it is the reason a
client can retry a timed-out POST without risking a duplicate run.

**Response `200`** — an `AgentResult`. The envelope grew across milestones; every field is
populated by the milestone named beside it:

```json
{
  "request_id": "33e066d4fa3d4265",
  "run_id": "0f9a...-...-...",
  "response": {
    "answer": "...",
    "reasoning": "...",
    "assumptions": ["..."],
    "confidence": "high | medium | low",
    "caveats": ["..."]
  },
  "llm_calls": [
    { "provider": "gemini", "model": "gemini-3.5-flash-lite",
      "prompt_tokens": 103, "output_tokens": 259,
      "latency_ms": 16732, "repair_attempt": 0, "error": null }
  ],
  "tool_outcomes": [
    { "call_id": "c1", "tool_name": "calculator",
      "arguments": {"expression": "17 * 3"},
      "output": {"result": 51}, "status": "OK",
      "error": null, "latency_ms": 2 }
  ],
  "tasks": [
    { "plan_ref": "t1", "description": "...", "state": "SUCCEEDED",
      "depends_on": [], "attempt_count": 1, "position": 0,
      "answer": "...", "error": null }
  ],
  "outcome": "COMPLETED",
  "agent_name": "researcher",
  "critic_verdict": "accept",
  "repair_count": 0,
  "total_tokens": 362,
  "latency_ms": 16743
}
```

| Field | Since | Why it is in the response |
|---|---|---|
| `run_id` | V0.3 | the handle for `GET /v1/runs/{id}`; `null` when persistence is off |
| `llm_calls`, `repair_count` | V0.1 | a caller can see what the request cost and whether the model had to be corrected. Cost and reliability should not be invisible to the caller paying for them |
| `tool_outcomes` | V0.2 | which tools actually ran, with their arguments and status |
| `tasks`, `outcome` | V0.4 | `PARTIALLY_COMPLETED` is a real answer, not a failure to classify |
| `agent_name`, `critic_verdict` | V0.7 | which specialist answered, and whether a critic accepted it |

### `POST /v1/goals/async`

Queues the goal and returns immediately. A worker process executes it.

**Mounted only when `AMOS_ASYNC_ENABLED=true`** (default `false`). Queueing with no worker
running leaves runs `QUEUED` forever, so async is an opt-in deployment decision rather than a
per-request one. The flag was read by nothing until 2026-09-13 while three documents instructed
readers to set it.

Same request body and `idempotency-key` header as the synchronous endpoint.

**Response `202 Accepted`**, with a `location` header pointing at where the outcome will appear:

```
location: /v1/runs/0f9a...-...-...
```
```json
{ "run_id": "0f9a...-...-...", "status": "QUEUED" }
```

`202`, not `200`: the work has been *accepted*, not *done*. Returning `200` would tell a client
the goal was completed when it has not started. Measured at ~54 ms, because no LLM call happens
on this path.

### `GET /v1/runs/dead-letter`

Runs the queue gave up on, newest first. `?limit=` defaults to 50, capped at 200.

**These are not ordinary failures.** A `FAILED` run executed and produced a verdict; a
`DEAD_LETTER` run never got one — the worker died on it `AMOS_WORKER_MAX_ATTEMPTS` times and the
queue stopped retrying so one bad run could not starve every good one. Each entry carries
`run_id`, `goal`, `attempt_count`, `last_worker`, `reason` and `dead_lettered_at`.

> **This route is declared before `/v1/runs/{run_id}` and has to be.** FastAPI matches in
> declaration order, so with the parameterised route first, `dead-letter` binds as a `run_id` and
> the request dies on the UUID check — a `422` on a path that exists. A test pins the ordering.

### `GET /v1/runs/{run_id}`

What exactly happened on a past request — assembled from stored rows only, which is what makes
it answerable for a run that happened weeks ago.

**Response `200`** — a `RunTrace`: `run_id`, `goal`, `status`, `request_id`, `result`, `error`,
`total_tokens`, `latency_ms`, `created_at`, `completed_at`, and four lists reconstructing the
execution — `tasks`, `steps`, `llm_calls`, `tool_calls`.

| Status | Condition |
|---|---|
| `404` | no run with that id |
| `422` | `run_id` is not a UUID |
| `503` | persistence is not configured, so there is nothing to read |

## Error envelope

Every error, from every endpoint:

```json
{ "error": { "type": "ProviderTimeoutError", "message": "...", "details": {} } }
```

`type` is the exact exception class name, so clients branch on a stable identifier rather than
parsing prose.

## Status codes

| Status | Condition | Retry? |
|---|---|---|
| `200` | Success | — |
| `202` | Goal queued for a worker | — poll `GET /v1/runs/{id}` |
| `404` | Unknown `run_id` | No |
| `422` | Request body failed validation (empty goal, missing field, non-UUID `run_id`) | No — fix the request |
| `429` | `ProviderRateLimitError` | Yes, with backoff |
| `500` | `ConfigurationError` or unhandled | No — server misconfigured |
| `502` | `ProviderAuthError`, `OutputValidationError` or `ToolLoopExhaustedError` | No |
| `503` | Persistence required but not configured | No |
| `504` | `ProviderTimeoutError` | Yes |

`502` for `OutputValidationError` is the considered choice: the request was valid and AMOS
functioned correctly — an upstream dependency (the model) failed to produce usable output after
every repair attempt. That is a bad gateway, not a bad request and not an AMOS bug.
`ToolLoopExhaustedError` joins it for the same reason: the loop cap did its job, and the model
failed to converge inside it.

Mapping lives in one table, `src/amos/api/app.py::_STATUS_MAP`. One table, so adding an error
type is one line.

## Not yet implemented

No authentication, no authorization, no rate limiting, no pagination, no list endpoint
(`GET /v1/runs` does not exist), no cancellation, no streaming or SSE, and no `/metrics`
endpoint — metrics leave over OTLP only.

Auth arrives when there is more than one user. Adding it now would mean a `users` table with one
permanent row (see `docs/05-data-model.md`, deliberate omissions). **AMOS is not currently safe
to expose publicly**; `docs/13-security.md` says so in more detail.
