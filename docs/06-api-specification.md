# 06 — API Specification

Conventions and contracts. The machine-readable schema is generated by FastAPI at
`/openapi.json` and `/docs`; this document covers what OpenAPI cannot express — versioning
policy, the error envelope, and status-code semantics.

**Current version: V0.1.**

## Conventions

- Versioned path prefix `/v1/`. Unversioned paths (`/health`) are operational, not product API.
- Request and response bodies are JSON. Every field is validated by Pydantic at the boundary.
- Every response carries an `x-request-id` header. A client-supplied `x-request-id` is honoured
  and echoed, so client and server logs correlate. This becomes the OpenTelemetry `trace_id` at
  V0.9.

## Endpoints

### `GET /health`
Liveness. Returns `{"status": "ok", "version": "0.1.0"}`. No auth, no dependencies checked —
deliberately shallow, so it stays fast and cannot fail for reasons unrelated to the process
being alive. A dependency-checking readiness probe arrives with the database at V0.3.

### `POST /v1/goals`

**Request**
```json
{ "goal": "string, 1..8000 chars" }
```

**Response `200`** — an `AgentResult`:
```json
{
  "request_id": "33e066d4fa3d4265",
  "response": {
    "answer": "...",
    "reasoning": "...",
    "assumptions": ["..."],
    "confidence": "high | medium | low",
    "caveats": ["..."]
  },
  "llm_calls": [
    { "provider": "gemini", "model": "gemini-3.5-flash",
      "prompt_tokens": 103, "output_tokens": 259,
      "latency_ms": 16732, "repair_attempt": 0, "error": null }
  ],
  "repair_count": 0,
  "total_tokens": 362,
  "latency_ms": 16743
}
```

`llm_calls` and `repair_count` are returned deliberately. A caller can see what the request
cost and whether the model had to be corrected — the same fields that become `llm_calls` rows
at V0.3. Cost and reliability should not be invisible to the caller paying for them.

## Error envelope

Every error, from every endpoint:

```json
{ "error": { "type": "ProviderTimeoutError", "message": "...", "details": {} } }
```

`type` is the exact exception class name, so clients branch on a stable identifier rather than
parsing prose.

## Status codes

| Status | Condition | Retry? |
|---|---|---|
| `200` | Success | — |
| `422` | Request body failed validation (empty goal, missing field) | No — fix the request |
| `429` | `ProviderRateLimitError` — free tier is ~15 RPM | Yes, with backoff |
| `500` | `ConfigurationError` or unhandled | No — server misconfigured |
| `502` | `ProviderAuthError` or `OutputValidationError` | No |
| `504` | `ProviderTimeoutError` | Yes |

`502` for `OutputValidationError` is the considered choice: the request was valid and AMOS
functioned correctly — an upstream dependency (the model) failed to produce usable output after
every repair attempt. That is a bad gateway, not a bad request and not an AMOS bug.

Mapping lives in one table, `src/amos/api/app.py::_STATUS_MAP`.

## Not yet implemented

No authentication (single user, local), no rate limiting, no pagination, no streaming. Auth
arrives when there is more than one user — adding it now would mean a `users` table with one
permanent row (see `docs/05-data-model.md`, deliberate omissions).
